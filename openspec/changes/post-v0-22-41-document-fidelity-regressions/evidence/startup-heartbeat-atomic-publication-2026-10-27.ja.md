# 起動検査の描画番号を完成した記録として公開する

## 実際の失敗と原因の境界

- 正式公開 run [40388796186](https://github.com/HiroyukiFuruno/KatanA/actions/runs/40388796186)、source `d2b78cefd967bb5995b3000facc2ace17366256b` の Linux job `121809877588` は、配布物のビルド・契約・生成物照合に成功後、起動検査で失敗した。
- エラーは `UI heartbeat could not be read after retries; last_frame=18`。描画番号が同じだったことを示す停滞エラーとは異なる。
- ログでは frame 19 の処理終了が `20:08:50.923740Z`、frame 20 の開始が `20:08:51.007162Z`、検査失敗が `20:08:51.293999Z`。frame 20 の終了は記録されていない。この時系列だけでは今回の原因を確定できない。
- 回収した実ログは `tmp/oct27-d2b78cef-linux-job-121809877588.log`、212881 bytes、SHA-256 `31f01e79157b892afccc23634b0e88ca6390b1c20a5ed578ff2b22923feb9caa`。

## 独立して確認した記録の不整合

従来の `std::fs::write` は公開中の記録を空にしてから書き直す。実ファイルを並行して読み書きする検査で、更新途中の空読みを再現した。ただし、この再現を上記 CI の原因確定とは扱わない。

新しい記録は、同じディレクトリに作成した一時ファイルへ全内容を書き、完成した記録へ置換する。初版の `NamedTempFile::persist` は Windows CI で読取中の宛先に対するアクセス拒否が見つかったため、現候補は書込ハンドルを閉じて `std::fs::rename` へ渡す。旧記録保持と並行読取を検査し、既存のエラーログ、描画番号の契約、毎フレームの記録を維持する。[Windows の不合格と修復](windows-open-heartbeat-rename-2026-10-27.ja.md) に OS 差と検証の限界を記録する。

## 検証と残件

- Linux 失敗時に保存済みの `heartbeat.txt` と `startup.log` を回収する経路を追加する。隔離設定ディレクトリはアップロードしない。
- 同経路の契約は旧 workflow で不足を検出し、補正後は既存の配布起動契約検査に成功した。既存の release flow 契約 20 件と actionlint も成功した。
- 実ファイルの旧スナップショット保持・並行読取・単調増加・相対パス・既存エラー記録を含む対象 Rust 検査 5 件、strict Clippy、rustfmt は成功した。旧書込処理へ一時的に戻す検証では、旧スナップショット保持の検査が意図どおり失敗し、修正を復元後に再成功した。
- 通常 commit/push、current review、全品質検査、新しい配布版の実起動は別工程として継続する。今回の Linux 失敗の解消、Windows の描画遅延解消、公開成功とはまだ主張しない。

元の 200ms 観測、10 回の進行確認、メモリ・フォント予算、本体照合、全 OS 同時公開の条件は変更しない。
